Arabic Tashkeel: Libraries, Models and APIs

Everything reviewed here does one job: take Arabic text and add the diacritics. No OCR. Ten open-source options and two commercial APIs, with the licence, the size, the published error rate and the source link for each, so every figure can be checked independently.

Short answer

Three tools cover almost every situation

CATT if you want the strongest published accuracy and can run PyTorch or ONNX. arabic-diacritizer if you want something that installs in one line, runs on CPU in 47 MB and needs no GPU. libtashkeel if it has to be embedded in a service with no Python at all. Everything else is either older, slower, more restrictively licensed, or a research artefact.

Do not use a general LLM for this. Two independent benchmarks say the same thing: CATT beats GPT-4-turbo by 9.36% relative DER, and the arabic-diacritizer authors measure GPT-5.3 at 20.9% DER against their own 6.6%. A purpose-built character-level model beats a frontier model here by a factor of three, at a fraction of the cost.

Before you compare the numbers below

These error rates are not on one scale. Shakkelha reports on the Fadel et al. 2019 test set; arabic-diacritizer and CATT report on Tashkeela; the Shakkala and Mishkal figures come from a third comparative study. Arabic DER also depends on two choices each paper makes differently: whether case endings (i'rab) are counted — the hardest part of the task — and whether undiacritized characters count as a class. Shakkelha's own tables show the same model scoring 1.69% or 1.34% depending purely on that choice. Treat the column as a rough tier, not a ranking.

There is no mature pay-per-call diacritization API market. Neither Google nor Microsoft publishes a standalone Arabic diacritization endpoint. Farasa is the best-known hosted option and is research-licensed. That absence is itself the finding: for this layer, self-hosting an open model is the normal path, not the fallback.

Read this as three tiers, not a ranking. Top tier — Shakkelha, Shakkala, CATT — sits at 2–3% and the differences between them are inside the noise created by different test sets and case-ending conventions. Middle tier — arabic-diacritizer at 6.6% — trades roughly half the accuracy for a very large gain in deployability. Bottom tier — Mishkal and general LLMs at 14–21% — is a different class of result entirely. The one robust conclusion is that a general LLM is the worst option on this list.

Which one to pick

Best accuracy

CATT

Apache 2.0, pip-installable, ONNX export. Encoder-decoder for accuracy, encoder-only for speed. Choose this if the diacritics are the product and you can carry a PyTorch or ONNX runtime.

Best to actually deploy

arabic-diacritizer

MIT, one-line install, 47 MB total, CPU only, CLI and Python API. Choose this if you want the layer working this afternoon and 6.6% DER is good enough for your use case.

No Python available

libtashkeel

Rust with C, Python and WASM bindings and an embedded model. Choose this for an edge device, a browser, or a service where adding a Python runtime is not an option.

1
Run all three on the same 20 sentences before choosing. Every number in this report was produced by a tool's own author on a public corpus. Your text — classical, modern, religious, technical — will shift these results, and the top three are close enough that your material decides between them.
2
Decide the case-ending question first. Case endings (i'rab) are the hardest part of diacritization and where most of the error concentrates. Shakkelha's own tables show 1.69% versus 1.34% on identical output depending only on whether they are scored. If your readers do not need full i'rab, the task gets materially easier and cheaper.
3
Never diacritize text that already carries diacritics. Strip-and-restore destroys marks a typesetter placed deliberately. Gate the call on a diacritic density check, and leave already-vocalised text alone — particularly in classical or religious material, where the printed marks carry meaning that context alone cannot recover.
4
Check the licence in the repository on the day you adopt. CATT moved from CC-BY-NC to Apache 2.0 mid-project. Shakkala and libtashkeel do not state a licence prominently. Farasa's research-only restriction lives on QCRI's website rather than in a LICENSE file. Do not rely on this table.

What it actually costs to run

None of the open-source tools above publish a per-call price — they are libraries, not APIs, so the only real cost is the compute you rent to run them. To answer this properly I installed two of them in a sandboxed 4-vCPU/3GB Linux VM and timed real inference, rather than repeating a vendor claim: Mishkal end to end, and arabic-diacritizer with its sentence cache switched off so the number reflects the neural model itself, not cache lookups. Both ran on a single CPU core, unbatched, processing one sentence at a time — the slow way. Cost below is $/vCPU-hour ÷ (words/sec × 3600), priced at $0.036/vCPU-hr (AWS c7g.large, on-demand, Jul 2026) for the CPU tools and the same $3.29/GPU-hr figure used elsewhere in this project for the dots.mocr estimate.

The headline finding is that compute is not the cost. Even measured the slow way — one sentence at a time, one core, no batching — diacritizing an entire 300-page book costs well under half a cent on the rule-based tool and under a cent on the neural one. Batching, which any real service would do, only lowers this further. What actually costs money is the engineering around it: a server to keep running, a wrapper API, monitoring, retries, and someone who owns it — the same conclusion this project reached for OCR self-hosting with dots.mocr. Budget for an engineer's time, not for tokens.

Caveats. The two measured numbers come from one small unbatched CPU core in a shared sandbox, not a dedicated benchmark host — treat them as a reasonable order of magnitude, not a guaranteed SLA. The CPU rate is a current on-demand list price for a small ARM instance; spot or reserved pricing would be lower. The CATT bracket is deliberately wide because no one publishes its throughput and it was not run here.

One repository to avoid

A repo named KSAA2026-Fine-Tashkeel ranks well for 2026 tashkeel searches and claims a shared-task result. Its README tells users to download a .zip from the repo's own analysis/ folder, run a Windows executable, and click past Windows security prompts and antivirus warnings. Zero stars, no releases, no contributors, no licence. That combination matches a common malware distribution pattern. Do not download or run it. It is named here only so nobody on your team does. The legitimate shared task is KSAA-2026 at OSACT7 / LREC 2026 — use the organisers' own materials. repository ↗
