One book, from a raw PDF to a fully corrected, reviewable, listenable result. This is the whole thing end to end, in the order it's actually meant to run — for deep detail on any single tool, see docs/tools-reference.html; for why the architecture is shaped this way, see docs/ocr-correction-architecture-built.html.

→Quick start — one command

tools/run_full_pipeline.py runs steps 1–9 below for you — both OCR engines, detection, arbitration, corrections, re-synthesis, and correlated-error detection — then stops cleanly at the one deliberately-manual review step. It's resumable exactly like every command it calls: a quota wall mid-run just means re-running the same line later.

VX2=/Users/ahmedmostafa/miniconda3/envs/vx2lm/bin/python3

# the whole book
$VX2 tools/run_full_pipeline.py "assets/PDF Samples/<book>.pdf"

# scoped to the first N pages -- same --pages convention as main.py
$VX2 tools/run_full_pipeline.py "assets/PDF Samples/<book>.pdf" --pages 2

# scoped to an explicit page range
$VX2 tools/run_full_pipeline.py "assets/PDF Samples/<book>.pdf" --pages 11:15

# page 13 through the end
$VX2 tools/run_full_pipeline.py "assets/PDF Samples/<book>.pdf" --pages 13:
--pages only scopes what gets freshly OCR'd
It's passed straight through to both OCR passes. Every later stage (detection, arbitration, correction, context detection) just operates on whatever pages already exist on disk for that book — so on a book with prior work, --pages 2 won't shrink an already-larger ensemble_review.json down to 2 pages; it only controls what's freshly fetched this run. For a truly isolated N-page run, delete work/<book> and work/<book>-lighton first.

Or, step by step

Set BOOK to your PDF's filename (without .pdf) and run this top to bottom — this is what the one-command version above does internally, useful for inspecting or restarting a single stage.

#    folders on its own, so move the Gemini result aside first

1Run both OCR engines

main.py auto-detects whether the PDF has a real embedded text layer — if so it uses the free/exact text-extraction path and ignores --ocr entirely, which means there's nothing to compare (both engines would be moot). Check first if you're unsure:

/Users/ahmedmostafa/miniconda3/envs/vx2lm/bin/python3 -c "
import fitz
doc = fitz.open('assets/PDF Samples/YOUR BOOK.pdf')
words = sum(len(p.get_text('words')) for p in doc)
print(words, '-> text-layer path' if words > 50 else '-> genuinely scanned, OCR matters')
"

The full Gemini-then-LightOn-then-rename sequence is in the quick start above (step 1-2). Each run does the whole normal pipeline itself — OCR, diacritize, TTS, reader — so you get two complete, independently-listenable books before any comparison even starts.

2Detect disagreements

tools/ensemble_review.py — diffs the two engines' text page by page, writes ensemble_review.json. Every other tool from here on reads that one file.

3Resolve them against the real image

tools/vlm_arbiter.py — one Gemini-vision call per flagged page (not per word), reads the actual pixels and writes what's really there. Updates ensemble_review.json in place.

4Apply the corrections

Two different tools for two different failure shapes:

If a page has...UseBecause
A handful of wrong wordsapply_corrections.pySubstitutes/deletes individual tokens, keeps the original in ocr_txt.
≥50% of words gemini-only (LightOn produced almost nothing)replace_page.pyInserting dozens of words one at a time is the wrong tool for a wholesale failure — this swaps the whole page's tokens for Gemini's.

Run the gemini-only ratio check (quick start step 5) before deciding — a page over the threshold should go through replace_page.py first, then whatever's left goes through apply_corrections.py.

5Re-synthesize the corrected pages

Both apply tools reset a touched page's status to "extracted" — run_tashkel.py and run_speak_gemini.py already skip anything past that stage for resumability, so this reset is what makes them naturally redo diacritization and audio for exactly the pages that changed, and nothing else.

6Catch errors both engines agreed on

tools/context_detector.py — the one gap nothing above can see: LightOn and Gemini agreeing on the same wrong word. Runs on every page's agreed-upon (KEEP) text using a text-only LLM (OpenRouter, kept off Gemini deliberately) as a linguistic plausibility check. Writes a separate file, context_review.json — never touches ensemble_review.json.

This model reasons before answering — expect real per-page latency
A page with 50-60 words to check can genuinely take several minutes. That's thinking time, not a hang — check CPU/network activity before assuming it's stuck (see tools-reference.html for how).

7Review and apply accepted suggestions

This is the one step in the whole chain that's manual on purpose — nothing from step 6 is ever auto-applied, because a text-only guess has no image behind it to check itself against.

  1. Build and open the review page: python3 tools/build_context_review.py "work/<book>-lighton/context_review.json" — sorted by suspicion, grouped by page with the real image alongside each flagged word, and a "different word" vs "case-ending only" tag on every entry.
  2. Prioritize the different word entries — those are the real correlated-error candidates. Case-ending entries are often just the automated diacritizer's own errors (~6.6% DER), more debatable.
  3. Edit context_decisions.json: "reject" → "accept" (take the model's proposal) or any other literal string (write your own correction — useful when, like the worked example in this project's own history, the model's proposal itself turns out to be wrong even though the error it found was real).
  4. Run apply_context_suggestions.py, then redo step 5.

8Get your results

work/<book>-lighton/reader.html — the normal reader: synced audio + text, boxes borrowed from Gemini's images where LightOn has none, flagged/verified words color-coded. work/<book>-lighton/context_review.html — the correlated-error review page from step 7. work/<book>-lighton/ensemble_review.json — the full audit trail: every token, both engines' reads, what got verified and how.

Optional, for a deep audit of a specific page range: tools/build_review.py builds a side-by-side original-vs-corrected view with two independent audio tracks. See tools-reference.html for that one — it's a separate, one-off tool, not part of this main sequence.

Everything in this chain is resumable
Every tool checks what's already done before spending an API call again — a 429 mid-run costs at most the one page it failed on. Re-running the exact same command later always picks up where it stopped.
