0The root cause: LightOn has no geometry

Two OCR engines exist in this pipeline. ocr_lighton.py's /parse endpoint returns markdown text only — no bounding boxes, ever. A support ticket in tmp/lighton_bbox_support_request.md confirms even /search's include_bboxes flag is broken (always []). ocr_gemini.py, by contrast, renders and saves the page image to disk and returns an approximate per-word box for every token.

That single asymmetry is why this became a two-engine comparison system instead of a single-engine self-correction system: you can't crop a word from an image if you don't know where it is. Gemini's OCR run of the same PDF became the reference every downstream tool leans on.

1Detection — how an error is found

NEWtools/ensemble_review.py

For a book that has both a LightOn OCR run and a Gemini OCR run of the same PDF, this diffs the two, page by page. Before comparing, both sides are normalized for comparison only — alif forms (أ/إ/آ/ٱ → ا), ة→ه, ى→ي, diacritics/shadda stripped, tatweel and punctuation removed. The stored/reported text is always the original, un-normalized form; normalization only decides equal-vs-not.

The two normalized word lists are aligned with Python's stdlib difflib.SequenceMatcher — not a hand-rolled aligner. Two OCR reads of the same page are difflib's strong case: mostly aligned, with a handful of localized edits, not two unrelated documents.

There is no "suspicion score"
Neither OCR engine emits a per-word confidence value, so this tool doesn't invent one. The action on every token is strictly binary:
ActionMeaning
KEEPBoth engines produced the same word (after normalization) — no error.
FLAGThe two engines disagree, or one produced a word the other didn't.

Result: ensemble_review.json per book — one row per token, {id, gemini_id, lighton_txt, gemini_txt, agree, action}. gemini_id records exactly which Gemini token a LightOn token aligned to; it's reused later to borrow that token's box for the reader.

Blind spot
Detection is purely disagreement between two engines. If LightOn and Gemini independently produce the same wrong word, nothing here catches it — that's exactly the "correlated errors" failure mode the original design doc (docs/ocr-correction-approaches-en.md §9.6) warned a pure ensemble is blind to. No separate linguistic/context suspicion model exists to catch that class of error.

2Correction — deciding what's actually right

NEWtools/vlm_arbiter.py

For every page with at least one FLAG, this sends the already-rendered Gemini page image plus the list of disagreeing candidates to Gemini vision — one API call per flagged page, not per flagged word. It works with no bounding box on either side, because it isn't cropping; it shows the whole page and asks the model to read specific spots.

The prompt deliberately does not offer a multiple-choice between the two candidates — it asks the model to read the image and write what's actually printed, diacritics included. That matters: a pure A-or-B choice can only ever be as right as the better of two wrong answers.

Two OCR engines transcribed this page and disagreed on the words listed
below. For each id, look at the image and write EXACTLY what is
printed there ... Do not just repeat either candidate if both are wrong;
write what you actually see.

The 17 novel answers were a mix — some were real fixes (Gemini's table-of-contents dot-leader noise, e.g. مُحَنّطَةً...................24, correctly cleaned to محنطة), some were riskier (an ISBN digit string got a third different grouping from either OCR read — not somewhere a VLM should be trusted blindly), and one was a literal empty string, meaning the model decided a word LightOn produced simply doesn't exist on the page at all.

Self-confirmation risk
Gemini vision arbitrates disagreements where Gemini's own earlier OCR read is one of the two candidates being judged. The prompt framing (a narrow "which is right at this spot" question, not a repeat of open-ended transcription) mitigates this somewhat, but it isn't a truly independent second opinion the way a different model or engine would be.

3Applying it — writing the correction back

NEWtools/apply_corrections.py — the first tool in this chain that writes to pXXX.json. Detection and arbitration only read/report.
VerdictWhat happens
Substitutiontxt is overwritten; the pre-correction word is kept in a new ocr_txt field, and "ensemble-vlm" is appended to the token's existing fixes[] list — same provenance pattern extract.py's clean_word() already used for its own fixes.
Empty verdict ("")The token is deleted outright. Safe because nothing downstream indexes by id — the reader walks tokens by array position, and the diacritizer re-matches by position against whatever's in the list after this runs.
gemini-only (word LightOn produced nothing for)Never auto-applied, on any book. Reported grouped by page instead. Inserting a word means guessing a position, minting an id, and sourcing a box — genuinely harder than substitution, and not something this pipeline decides automatically.

Any page that gets a correction has its status reset to "extracted" — run_tashkel.py and run_speak_gemini.py already skip anything marked "diacritised"/"spoken" for resumability, so this reset makes them naturally redo diacritization → TTS → alignment for the touched page. Without it, the audio would keep narrating the pre-correction word forever.

Coverage gap this leaves on every book
Because gemini-only words are never auto-inserted, a book that only ran through apply_corrections.py is still missing words that Gemini saw and LightOn didn't — not just occasionally wrong ones. That gap is only closed where replace_page.py's threshold catches the page (next section), or by a manual insert.

4Whole-page failures — a different fix for a different failure

NEWtools/replace_page.py

Found by actually looking at the data: page 16 of the pilot book had 74 of 75 tokens as gemini-only — LightOn didn't misread a few words there, it failed almost entirely. Looking at the actual page image explained why: white text reversed out of a dark olive background, with a ghosted watermark illustration bleeding through behind it — a genuinely hard case for a small 1B-parameter OCR model, not a fluke.

For a page like that, inserting 74 words one at a time is the wrong tool. replace_page.py instead wholesale-swaps the page's entire token list for Gemini's — safe because both engines' OCR code already emits the identical token schema (id/raw/txt/fixes/box). It's threshold-gated (default ≥50% of a page's tokens being gemini-only) specifically so it can't accidentally swap a page that just had ordinary word-level disagreements, which belong to apply_corrections.py instead.

Side effect worth knowing
A wholesale-replaced page loses LightOn's original ids — they become Gemini's. Any tool trying to pair "what LightOn originally said" against "the current corrected token" by id (like build_review.py's inline text pairing) can't do that for a replaced page anymore; it has to fall back to sourcing the original text from ensemble_review.json's untouched historical record instead.

5Seeing it — the two reader tools

MODIFIEDsrc/pipeline/build_reader.py — affects every book, not just the pilot

Optionally reads ensemble_review.json if a book has one (additive — a book with none builds exactly as before). Flagged/verified words get distinct highlight colors with correction detail on hover.

The bigger change: when a LightOn page has no boxes of its own, the reader does a fresh, on-the-fly re-alignment (reusing ensemble_review.py's align_page(), never persisted, run against today's possibly-already-corrected text) to borrow the paired Gemini page's box and rendered image. It only does this if every current token on that page gets a borrowed box — otherwise the page stays honestly text-only rather than half-rendering. That turned what used to be one global "does this book get the compare view" switch into a per-page decision.

NEWtools/build_review.py — a separate, one-off comparison view

Not wired into build_reader.py — scoped deliberately to a specific page range of one book. Builds two independent, fully-synthesized audio tracks per page (original-OCR text vs. corrected text), each with its own Gemini TTS + Whisper alignment pass, plus inline strikethrough-original → bold-correction text pairs and color-coded image boxes.

"Original" text is sourced from ensemble_review.json's lighton_txt directly — deliberately decoupled from per-token id pairing, because that pairing breaks on a wholesale-replaced page (previous section). This is why page 16 still gets a real (near-silent) original-audio track even though its ids no longer match anything in ensemble_review.json for per-word highlighting purposes.

Real constraint hit while building this
gemini-3.1-flash-tts's free tier caps at 10 requests/day. Both TTS-heavy tools (run_speak_gemini.py and build_review.py) are resumable — an already-synthesized .wav on disk is reused rather than re-spent — specifically because this quota is real and gets hit repeatedly on an active book.

6What this does NOT do

Worth having in one place rather than scattered across five tools' docstrings:

  • No context/suspicion model.Detection is purely engine disagreement. Two engines agreeing on the same wrong word is invisible to this system.
  • No independent verifier.The VLM arbitrator is the same model family as one of the two OCR candidates it's judging.
  • Not every "VERIFIED" word deserves equal trust.~7% of verdicts are novel third answers; a couple (numeric codes) are genuinely lower-confidence than the flat VERIFIED label implies.
  • Missing words are never auto-inserted.apply_corrections.py reports gemini-only gaps but never fills them, on any book — only a whole-page replacement via replace_page.py closes that gap, and only above its threshold.
  • Requires a paired Gemini OCR run.A LightOn-only book with no matching Gemini run of the same PDF has no error-detection path at all right now — every tool in this chain reads ensemble_review.json, which can't exist without that pairing.
