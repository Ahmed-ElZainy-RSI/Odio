System design & proof of concept

Scanned Arabic books → synced read-along

The complete pipeline, traced end to end on one real page: السماء (The Sky), page 5. The audio below is real — synthesised by Hume with real word-level timestamps. Every text transformation is real data from this repo, verified against the printed page.

Data-integrity finding, discovered while building this

The OCR file sam_2/الشمس.txt is not الشمس.pdf. Its content matches السماء.pdf (The Sky) page-for-page. The cover reads الشمس but OCR transcribed the stylised title as لولو, and the deposit/ISBN numbers disagree with the PDF (2022/2173→2175, …1367→…1381). All audio generated so far is filed under the wrong book. Design consequence: the page record must carry a verified source-PDF hash, not a filename.

Token anchoring — one id, four representations

The invariant that makes sync possible. Correction changes وَجُزْيَيَاتِ→وَجُزْئِيَّاتِ (different length) and diacritization changes length again — so string offsets shift at every stage. The id never does.

Two phases — sweep small, run big

Brute-forcing every option across the full catalogue is arithmetically impossible. The sweep runs on 3 sample books; production runs one locked config.

What this one page proves

ClaimEvidence
Tashkeel presence ≠ correctnessThis line is fully diacritized and still carries 2 letter errors + 1 wrong diacritic.
A diacritizer cannot fix itالفضل is a valid word — it diacritizes cleanly to "grace" where the page says "classroom".
Correct → then diacritizeReverse the order and the error is locked in under confident marks.
String offsets can't anchor syncوَجُزْيَيَاتِ→وَجُزْئِيَّاتِ changes length; a stable id survives it.
Native timestamps make sync exactHume returned 12 word timings for 12 tokens — no alignment model, no drift.
Filenames are not provenanceThis file is named الشمس and is actually السماء.
