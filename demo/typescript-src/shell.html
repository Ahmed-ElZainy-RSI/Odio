تحت الغطاء · Under the Hood

Why TypeScript, here — with proof, not marketing

Three concrete things strict TypeScript caught or enforced while building this exact page — not generic language-comparison talking points.

1. The pricing data is three shapes, not one number

models/cost.md mixes a metered per-page rate, FastOCR's flat $249.95 pack fee, and Besser OCR's monthly subscription into a single markdown table — which is exactly how it ended up self-contradictory (a "$249.95 per 50,000 pages" row that can't be reconciled with "$249.95 for this one 5-page run"). Modeling it as a discriminated union keeps each shape honest instead of forcing a misleading single $/page field:

type CostTier =
  | { kind: "metered"; low: number; high: number }
  | { kind: "flatFee"; amount: number; forPages: number }
  | { kind: "subscription"; monthlyAmount: number; pageCapPerMonth: number };

2. The compiler enforces every case is handled — forever

The dot plot, the table, and the tooltip all normalize a CostTier through the same assertNever-guarded switch. To prove it's real, not aspirational, I added a fourth pricing shape to the type (perCall) without touching the switches — and tsc --strict refused to compile:

src/app.ts(101,26): error TS2345: — costToChartBasis(), converts
  a CostTier to the chart's $-per-50,000-pages figure
src/app.ts(116,26): error TS2345: — same error, costRangeLabel()
src/app.ts(125,33): error TS2345: — same error, costKindLabel()
  Argument of type '{ kind: "perCall"; amountPerCall: number; }'
  is not assignable to parameter of type 'never'.

Three exact locations, found before the page ever loaded in a browser. The equivalent plain-JS version would just silently render NaN for the new tier's dot position and ship it.

3. It caught a real bug in this page's own code

The generic DOM helper below failed to compile on the first pass — strict mode rejected casting a plain HTMLElement straight to an arbitrary generic T, since nothing guarantees T is actually a subtype of what createElement returns:

function must<T extends Element = Element>(id: string): T {
  const found = document.getElementById(id);
  if (!found) throw new Error(`#${id} is missing from the DOM`);
  return found as unknown as T; // ← tsc forced the honest "as unknown as" step
}

Small, but it's the same class of mistake (an unchecked cast papering over a real type mismatch) that causes real runtime crashes — caught here at compile time instead of during a demo.

4. Model ids are a closed, typo-proof set

type ModelId = "lighton" | "datalab" | "paddleocr" | "fastocr" | "baseerocr" | "glmocr" — every lookup, tab, and DOM binding is checked against this union. Typing "glm_ocr" instead of "glmocr" anywhere is a compile error, not a silently-undefined panel at runtime.

5. The three themes above can't ship half-finished

The Manuscript / Blueprint / Terminal picker is backed by Record<ThemeName, Record<ThemeMode, ThemeTokens>> — a mapped type, not a switch. Delete the dark entry for "terminal", or drop one field from ThemeTokens, and every theme instantly fails to compile until it's filled back in:

type ThemeName = "manuscript" | "blueprint" | "terminal";
type ThemeMode = "light" | "dark";

const THEMES: Record<ThemeName, Record<ThemeMode, ThemeTokens>> = {
  manuscript: { light: {...}, dark: {...} },
  blueprint:  { light: {...}, dark: {...} },
  terminal:   { light: {...}, dark: {...} }, // ← miss this and tsc refuses to build
};

There is no code path where "Blueprint, dark mode" quietly falls back to undefined CSS variables and unstyled text — it either exists at compile time, or the page never ships.
